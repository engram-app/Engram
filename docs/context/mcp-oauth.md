# MCP OAuth 2.1 + DCR + CIMD: How It Works

_Last verified: 2026-10-16_

End-to-end OAuth 2.1 + Dynamic Client Registration on Engram's MCP endpoint, so Claude Connectors / Cursor / ChatGPT custom GPTs / any other standards-compliant client can auto-auth against `mcp.engram.page/api/mcp` (saas) or `engram.ax/api/mcp` (selfhost) without per-client integration code.

> **Host note:** the saas MCP endpoint is `mcp.engram.page`, NOT `app.engram.page` (the SPA). See workspace `../engram-workspace/docs/context/public-url-host-split.md`. All curl examples below use `mcp.engram.page`.

## Wire flow (what Claude Connectors actually does)

```
1. GET  /.well-known/oauth-protected-resource    → {resource, authorization_servers}
2. GET  /.well-known/oauth-authorization-server  → endpoints + grant_types + PKCE
3. POST /oauth/register                          → mints client_id (DCR)
4. GET  /oauth/authorize?client_id&redirect_uri  → 302 to /oauth/consent (SPA mediation, Phase 7.A)
5. SPA reads URL params, fetches /api/oauth/clients/:id for client_name, renders consent
6. POST /api/oauth/authorize/consent {vault_choice} → JSON {redirect_uri: "..."} (SPA window.location)
7. POST /oauth/token grant=authorization_code    → access_token + refresh_token
8. POST /api/mcp Authorization: Bearer ...       → tool calls (vault-locked)
9. POST /oauth/token grant=refresh_token         → rotated tokens (RFC 6749 §10.4 family)
10. POST /oauth/revoke                           → 200 once the client authenticates (RFC 7009)
```

CIMD clients (Claude, ChatGPT) skip step 3: they send an HTTPS URL as `client_id`, and `/oauth/authorize` fetches that metadata document. See `cimd-vs-dcr-validation-policy.md`.

## Endpoint reference

| Method + path | Auth | Purpose |
|---------------|------|---------|
| `GET /.well-known/oauth-protected-resource` | none | RFC 9728 — points clients at `/api/mcp` + lists auth server |
| `GET /.well-known/oauth-authorization-server` | none | RFC 8414 — server metadata (endpoints, grant types, PKCE S256, scopes) |
| `POST /oauth/register` | none, rate-limited 60/IP/min | RFC 7591 DCR. Public (`none`) or confidential (`client_secret_post` / `client_secret_basic`, secret returned once); PKCE mandatory either way |
| `GET /oauth/authorize` | none, rate-limited 10/IP/min | Validates request, 302s to `/oauth/consent` (SPA mediation, Phase 7.A) |
| `GET /api/oauth/clients/:client_id` | none, rate-limited 10/IP/min | Public client metadata for the consent UI: `client_id`, `client_name`, `kind`, `slug`, plus `redirect_uri_registered` / `redirect_host` / `redirect_loopback` for the `redirect_uri` query param, and `client_host` (the host of a metadata-document client_id, shown as "App details from"). The page refuses an unregistered redirect and offers Cancel only for one the backend confirmed (fails closed, wizard Cancel too), shows the host (`scheme://host` for an app scheme), and warns on a localhost redirect |
| `POST /api/oauth/authorize/consent` | Bearer JWT | SPA submits w/ `vault_choice`. Mints code. JSON `{redirect_uri: "..."}` for SPA `window.location` |
| `POST /oauth/token` | client auth, rate-limited 300/min per {client_id, IP} plus 3,000/min per IP | RFC 6749 §3.2 — auth code → tokens, refresh → rotated tokens |
| `POST /oauth/revoke` | client auth, rate-limited 300/min per {client_id, IP} plus 3,000/min per IP | RFC 7009. Client auth is `EngramWeb.OAuthClientAuth`, shared with `/oauth/token` (body id, Basic, or assertion; an assertion's `aud` may be the revoke URL). Bad auth is 401 `invalid_client`, a missing `token` is 400 `invalid_request`, an access token is 400 `unsupported_token_type`; otherwise 200 whether or not the token existed |

## Token model

- **Audience binding (RFC 8707, #1977)** — Shipped staged in 0.53.0 (verify both audiences) and switched on in the next release, because a node on an older release 401s `engram:mcp` during a rolling deploy. Rolling back past 0.53.0 would 401 every live MCP access token until it refreshes. OAuth access tokens carry `aud: "engram:mcp"` (`Engram.Token.mcp_audience/0`) and resolve only on routes declaring `private: %{token_surface: :mcp}`: `POST /api/mcp` and `POST /api/attachments` (the `get_attachment_upload_target` tool tells clients to upload there with the same token). Everywhere else, REST and the sync socket, they get 401 `invalid_token` via `TokenResolver.resolve/2`, checked before any verifier because on self-host the Local provider would accept them as sessions. A `resource` naming another host is `invalid_target` at authorize and token (after client auth there; host case-insensitive; empty is absent). Device-flow tokens keep `aud: "engram"`. An MCP scope (`mcp` or `mcp:read`) is required on MCP-audience tokens (403 `insufficient_scope`).
- **Access token** — internal HS256 JWT minted by `Engram.Accounts.generate_jwt/2` from `OAuth.token_claims/1`. 15-min TTL. Carries `gid` (the grant's refresh-token `family_id`), which `Accounts.grant_claims/1` resolves server-side on every read (`OAuth.expand_claims/1`, cached per family in `Engram.Cache` `:oauth_grant`, evicted by the `oauth_refresh_tokens_changed` NOTIFY trigger and, per changed family, by every revoke: `OAuth.grants_changed/1`). The grant's ROWS are the single authority: the cached state carries the family's owner (a `gid` naming another user's family is `:revoked`, even in a token we signed), its levels, its `vault_ids` (a pre-levels grant's vault list is read from the row, never the token: vault deletion narrows the row after tokens were minted) and `granted_at`. A family is live only while NO row of it is revoked, never "its latest row by `inserted_at`" (app clock): one rule, `OAuth.family_unrevoked/1` (a query macro), read by enforcement, rotation, cleanup, the connections list and the connection-cap count alike. `EngramWeb.Plugs.Auth` refuses a revoked grant with 401 itself, before activity, fingerprint and rps plugs run, on both token-JWT branches (self-host resolves OAuth tokens as provider JWTs), and hands the claims to `OAuthScopeEnforce`. A Clerk JWT is never read as a grant (`Engram.Auth.provider_tokens_carry_grants?/0`: only the `:local` provider can carry one). `UserSocket` refuses a revoked grant with the same `auth rejected` log line and `[:engram, :auth, :rejected]` event (`reason: grant_revoked`, `source: :socket`) as any failed auth. Every revoke path (connections page one grant / client-wide / with `vault_id`, vault soft delete and its narrowing, the purge pass, replay, RFC 7009) also disconnects the owner's sockets after commit (`SessionInvalidator`, per user: sockets carry no grant id), and a `crdt:` join re-resolves the grant from the cache, refusing a revoked one (`unauthorized`) and judging the vault on what the grant reaches now. Measured: 0 grant queries warm, 1 cold (`query_budget_test.exs`, "mcp get_notes oauth").
- **Refresh token**: `engram_oauth_rt_<...>` opaque random, sha256-hashed at rest. 90-day TTL. Stored in `oauth_refresh_tokens` with a `family_id` per RFC 6749 §10.4. Rotation on use; replay of a consumed token revokes the entire family, except inside the 60 s grace window below. Rotation takes the user's grant lock (`OAuth.lock_grants!/1`, an advisory lock vault deletion's narrowing also takes) BEFORE `FOR UPDATE` on the presented row, always in that order, and the successor copies the row as the consuming UPDATE's RETURNING left it, so a concurrent narrowing is never undone by the new row (`Engram.OAuthRotationNarrowingRaceTest`). Every revoke (`OAuth.revoke_refresh_tokens/2`) takes the same grant lock per owner, then row locks ordered by id: locking rows first deadlocked against a rotation, and the aborted side raised a 500 (`OAuthRotationRaceTest`). The first family's id is the authorization code's id, so a replayed code (past the same 60 s, before the code's own 10-min expiry, and only after its client and PKCE checks pass) revokes everything it issued (RFC 6749 §4.1.2), refused as reason `code_replay_revoked`. The device and local-auth paths have their own leeway (see `refresh-token-reuse-detection.md`).

### Refresh grace window (#1974) and its tradeoff

A client whose rotation response is lost retries with the token it still holds. Before #1974 that revoked the family, so every lost response killed the connection. Now a replay of a consumed token **within 60 s**, while its successor has **never been used**, re-issues: the unused successor is revoked and one new successor is minted, so the family never has two live tokens. Every duplicate inside the window is handled the same way, up to **5 re-issues per token**; the window is anchored at the token's first use (`consumed_at`, set once), so replays cannot slide it. The 6th replay is reuse and revokes the family. The count is the successor rows the re-issue already locks, so no column is needed (Hydra caps the same way, `used_times < N`).

Every decision about a refresh token runs in one transaction holding `FOR UPDATE` on the presented row, so rotations of one token serialize and the second sees the first one's result. Every Disconnect path revokes through `Engram.OAuth.revoke_refresh_tokens/2`, which first locks the live rows (waiting for any rotation holding one) and then revokes with a fresh statement, so a successor a rotation just committed is revoked too. `Engram.OAuthRotationRaceTest` proves both on separate committing connections.

The cost: inside the window, whoever presents the consumed token first gets the new one. What bounds it:

- The replay must come from the **same `client_id`** (`:client_mismatch` otherwise), and a `private_key_jwt` or secret client must pass client authentication first (the token controller authenticates before `rotate_refresh_token/3` runs).
- Nothing minted since may have been **used**: a consumed successor means the client had it, so the replay is theft and the family is revoked.
- At least one successor must still be live: one revoked any other way (RFC 7009, Disconnect) is never resurrected by replaying its parent.
- A token found revoked under the lock is refused as `refresh_token_revoked`, not logged as reuse.
- The successors are locked and the revoke must hit every live one read; anything else is treated as reuse.
- If the successor the grace revoked turns up later, two parties held the lineage: the `revoked_at` clause revokes the family.
- Successors are found by lineage (`parent_id`, migration `20261015070000`, set on every rotation and re-issue), never by `inserted_at >= consumed_at`: those are two app-node clocks, so a re-issue minted on a lagging node was invisible to the next replay and a client's later use of it went undetected. A row without `parent_id` (a family's first row, or one a pre-`parent_id` release minted mid-deploy) falls back to the time test.
- Every re-issue logs `oauth_refresh_grace_reissue` with `client_id`, `family_id` and `ip_matched` (whether the replay came from the IP that received the successor). `ip_matched=false` is the line to read when looking for theft; it is not refused, because a vendor backend (ChatGPT, Claude) may retry from a different egress IP.
- **Grace and family-wide liveness (#174).** A grant is live only while no row of its family is revoked (`OAuth.family_unrevoked/1`). The successor a grace re-issue revokes is therefore also stamped `superseded_at` (migration `20261015050000`), which `family_unrevoked/1` and the cleanup reaper skip: the re-issued grant stays live, while the superseded row itself still never mints (presented later, it revokes the family). Rotation judges a CONSUMED row first, even when it is also revoked (an RFC 7009 revoke marks every row of the family), so replaying a used token is reported as reuse, as before; grace additionally needs a live family. A revoked row, or any row of a revoked family, is `refresh_token_revoked`.
- **Rows written before `superseded_at` (0.52.0 and rolling deploys).** 0.52.0's grace re-issue (#1981) revoked the replaced successor WITHOUT `superseded_at`, and an old node keeps doing so until a rolling deploy finishes. Read naively, each such row is a family revoke and kills a real connection on deploy. So `family_unrevoked/1` also excuses a revoked row that was never consumed while its family still has a live (unconsumed, unrevoked) row: that shape is only ever a superseded successor. A real family revoke marks every live row and a single-row RFC 7009 revoke of the live leaf (main before #174) leaves none, so neither is excused (`OAuthGrantStateTest`, "a grace-superseded row written without superseded_at"). Because liveness is right from the first boot, there is no deploy race. Migration `20261015060000` then stamps `superseded_at = revoked_at` on matching rows, and `OAuth.backfill_superseded/0` re-applies the same predicate at the top of the hourly `cleanup_expired/0` (before the reap, which keys on `superseded_at`) for rows old nodes write mid-deploy. Zero operator action.
- **Codex <= 0.163 trips reuse detection (2026-10-24).** Codex has two refresh paths; the in-request one takes no cross-process lock and persists the rotated token late, so a second Codex process presents a consumed token minutes later (outside the 60 s grace), the family is revoked (correct), and Codex retries the dead token forever (openai/codex#46028, #48507). Fixed by coordinated refresh in Codex 0.164.0. We kept the rules strict; #2185 counts families killed (`engram_prom_ex_oauth_family_revoked_total{client_agent,reason}`), logs `superseded_reuse`, and tags `mcp_client_connected` with `client_version`. Alert on families killed, never on rejected exchanges (638 of 639 Codex rejections on 10-23 were retries of one dead family; engram-infra#1579). Cross-project write-up in the Engram vault: `50 Engineering/Auth, MCP & Identity/Codex MCP OAuth Refresh Race.md`.

## Scope grammar

Values minted at consent:
- `mcp` — identifies as MCP-server token (vs general-purpose internal JWT); full read + write
- `mcp:read` — read-only grant (#174, required by Meta Muse's directory). Minted when the client asks for `mcp:read` alone, or when the user's pick on the consent screen grants Write nowhere (`read_only: true` on the consent POST, which can only narrow). The picker has no Read only switch: "All vaults" is one Read/Write row, "Choose vaults" a row per vault plus vaults created later, all starting unchecked (Review stays disabled until something is picked). With Write unchecked on every row, in either mode, the SPA sends `read_only: true`, so the AI sees no write tools, matching the pick (for "Choose vaults" this is deliberate, not an accident of the old switch). API keys have no scope and store levels only. Scopes are a union: `mcp mcp:read` is full access, because MCP clients may request every advertised scope. `mcp:read` caps every per-vault level (below) at read. Refresh copies `scope` unchanged.
- `vault:<id>` — bound to one vault. Any tool call with a different `vault_id` arg is rejected by `EngramWeb.Plugs.OAuthScopeEnforce` + `McpController.resolve_mcp_vault/3`.
- `vault:*` — all user's vaults. Tool calls choose `vault_id` per-call.

Scope is propagated through code → refresh token → access JWT. Today the JWT carries `vault_id` as a separate claim (not parsed from the scope string): simpler enforcement, same effect.

### Per-vault access levels (#174 OAuth, #332 API keys)

A grant or API key holds a level per vault (`none` | `read` | `write`) plus a **new-vaults policy**: the level for every vault it does not list, including vaults created after it. "All vaults" on the consent screen is just an empty list plus that policy. The policy is resolved at REQUEST time, never by writing rows when a vault is created, so it needs no backfill.

- **One representation** for both credential kinds: `Engram.Permissions` scope (`:all`, or `%{vaults: %{id => level}, default: level}`). `vault_scope/1` intersects an API key's scope with an OAuth grant's (lower level per vault). Enforcement asks `allows?/2` (read) or `allows_write?/2`.
- **Storage.** OAuth: `vault_access` (jsonb) + `default_access` (text) on `oauth_authorization_codes` and `oauth_refresh_tokens`. API keys: `api_keys.default_access` + `api_key_vaults.level` (NULL = write). NULL everywhere = the pre-levels meaning (listed vaults write; no list = every vault write). Selections go through `Permissions.resolve_access/2`: listed vaults must be the user's active ones; with a `none` policy the redundant `none` entries are dropped (token size); with a non-`none` policy every vault soft-deleted at creation is recorded `none`, so "vaults you create later" never covers a deleted vault that is restored later.
- **Token.** `Engram.OAuth.access_claims/1` builds a grant's full claims (`vault_access`, `default_access`, plus the legacy `vault_ids`/`vault_id`); `Permissions.from_claims/1` reads them back. The connections list reads a grant through the same pair, so display and enforcement cannot drift. The ACCESS TOKEN (`token_claims/1`) carries no per-vault map: only `gid` + the legacy `vault_ids`/`vault_id`, capped at 16 ids (past that the sentinel, so a pre-levels node reaches nothing). The levels come from the grant's rows via `gid`, so the token stays under ~2 KB at any vault count (pinned with 500 vaults).
- **Consent / key creation.** `vault_access` (`{id: level}`) + `default_access` on `POST /api/oauth/authorize/consent`, `POST /api/api-keys` and `POST /api/connections/pat`, parsed by `Permissions.parse_access_params/1`. An absent policy is `none`. A selection that reaches nothing is refused. Listed vaults must be the user's own.
- **Old backend + new SPA.** A backend that predates levels ignores `vault_access`/`default_access`/`read_only` and mints full access. So the SPA shows the Read/Write level pickers only when `GET /api/vaults` (and the bootstrap's embedded copy) carries `access_levels: true`. Both responses also ECHO what was stored (`Permissions.to_params/1`): consent returns `granted: {scope, vault_access, default_access}`, key creation returns `vault_access` + `default_access`. The SPA refuses to follow the consent redirect, and deletes a just-created key, when the echo is missing or wider than the pick.
- **Enforcement**, all call-time:
  - MCP: `tools/list` hides write tools only when NO vault is writable (`writable_anywhere?/2`); otherwise `tools/call` checks the resolved vault and refuses with a tool result (`isError: true`) naming it as read-only, the same shape as a no-access vault. A write tool called under a grant with NO writable vault stays a -32602 protocol error: that tool is absent from the credential's `tools/list`, so it is an unknown tool to the client. Every write gate asks `Tools.writes_vault?/1`, kept apart from `readOnlyHint` (which tells a client to confirm first): `send_feedback` is not read-only but writes no vault data (it reaches the Engram team), so `mcp:read` and all-read grants may list and call it. `get_attachment_upload_target` is a vault write (`readOnlyHint: false`): it hands out where to upload with this credential.
  - REST: `VaultPlug` 403 `read_only_vault` on a write to a read-level vault. `OAuthScopeEnforce` 403 `read_only_grant` on any write when the request's credential, of ANY kind (`Permissions.vault_scope/1`: grant or API key), can write nothing; that covers account-level routes no vault check guards (`PATCH /api/me`, onboarding actions, telemetry, vault registration). "Write" is defined once, in `EngramWeb.ReadOnlyRoutes` (non-safe methods minus the POSTs that only read: `/api/mcp`, `/api/search`, `/api/billing/plan-change/preview`).
  - Claims: `OAuthScopeEnforce` and `UserSocket` read a grant's claims with `Accounts.grant_claims/1` (signature checked, `exp` not re-checked, since the resolver just validated the token), so a token expiring between the two reads cannot read as claim-less (= unrestricted). An internal-JWT request whose claims still cannot be read is 401, never unrestricted.
  - Vault lifecycle (`VaultsController`): rename/delete need write on the vault, restore an explicitly listed write (same 403 body as out-of-scope, no oracle); purge stays session-only (`RequireSession`), so no grant or key reaches it; creating a vault needs a `write` new-vaults policy.
  - Socket: every write rides `crdt:`, so a read-level vault is refused at `crdt:` join (`read_only_vault`); `sync:` and `user:` (no inbound writes) still join, so a read-only credential may connect and listen. `UserSocket` reads the grant claims once per connect (`read_claims/1`).
  - No plan gate on API-key writes: #1974 opened API keys to every route on every tier and deleted `RequireApiWriteEnabled`, so MCP applies only the credential's own levels (no `api_write_not_available`).
  - "Writable anywhere" (the account-level gate, MCP `tools/list`) and "reaches anything" (revocation) count only LIVE listed vaults (`writable_anywhere?/2`, `reaches_anything?/2`): a level on a deleted vault grants nothing. Restore passes the account gate for the vault it names.
- **Rollback / mixed versions: fail closed.** A release that predates levels reads only `vault_ids`/`vault_id` (each id = write, NULL or `[]` = every vault), copies only those columns when it exchanges a code or rotates a refresh token, does not know `mcp:read`, and looks API keys up by `sha256(raw)` reading `api_key_vaults` rows as write (no rows = every vault). So:
  - **OAuth:** a leveled grant's `vault_ids` (column and claim) lists ONLY its write-level vaults. With none (write only through the policy, every level read, or `mcp:read`) it is `["00000000-0000-0000-0000-000000000000"]`, an id no vault has; never NULL/`[]`. The scalar `vault_id` column is a FK with ON DELETE CASCADE, so a leveled grant always leaves it NULL (naming a vault there would delete the whole grant when that vault is purged; every reader since 2026-09 reads the array first); the scalar claim carries the first write id or the sentinel. A pre-levels list keeps its first id in the scalar, repointed off a deleted vault when the array is narrowed. An old node therefore grants write on genuine write vaults only, read vaults go invisible, policy-only and `mcp:read` grants reach nothing. The new code reads `vault_access`/`default_access` and ignores the sentinel; a grant an old node rewrote (levels dropped) reads as write-vaults-only or nothing. Two selections an old node already reads exactly stay legacy-shaped: every vault at write (NULL, only while nothing is in the trash) and a plain vault list, under the full `mcp` scope. With a vault in the trash, "every vault at write" (new SPA, or `:all` from a stale one, normalized to the new SPA's pick) is ONE leveled grant: every live vault listed at write, the trashed ones `none`, policy write. Its legacy `vault_ids` lists the vaults live at consent, so an old node writes those and never the restored one (narrowed during a rollback, never widened: NULL would hand an old node the restored vault). Pinned by `test/engram/vault_access_compat_test.exs`, which runs origin/main's reader on new rows and claims.
  - **API keys:** a sentinel row is impossible (`api_key_vaults.vault_id` is a FK to `vaults`), so a leveled key is stored under a versioned hash an old release never computes: raw form `engram_lk_` + 43 chars, stored `sha256("leveled:" <> raw)`. An old release answers 401 for it (it cannot be widened at all); pre-levels keys (`engram_` + 43, plain hash) are unchanged, and the length difference means the two forms cannot collide.
- **Vault deletion: one rule for grants and keys.** A credential is revoked when it reaches no LIVE vault (`reaches_anything?/2` over the user's active vaults: no live listed vault at read/write and a `none` policy). Soft delete applies it to OAuth grants (`Connections.revoke_by_vault/2` → `drop_vault_from_grants/3`: pre-levels grants listing the vault among others are narrowed and their scalar repointed off it, a pre-levels grant whose only vault it was is revoked; leveled grants are judged on their levels, never on `vault_ids`, reading only unconsumed rows and revoking by `family_id`; their levels are left intact); purge runs the same `drop_vault_from_grants/3` for OAuth grants BEFORE the vault row goes (the scalar FK cascades, so a grant soft delete missed would otherwise vanish uncounted), and the key rule for API keys (`CleanupVault`). Revoked grants are counted (`revoked_oauth_grants`) and their owner's sockets disconnected. A credential with a non-none policy keeps working.
- **Client-wide revoke with `vault_id`** (`DELETE /api/connections/oauth/:client_id?vault_id=`, `revoke_oauth_family/3`): revokes, whole, every leveled grant that can reach the vault (read, write or policy); pre-levels rows match the vault in `vault_ids`, or in the scalar `vault_id` only when the array is unset (a grant narrowed off the vault no longer reaches it, whatever its scalar says), and an all-vaults NULL grant of the client is revoked too: it reaches every vault.
- **Editing access from Settings** (`PATCH /api/connections/oauth/:client_id?family_id=`, `PATCH /api/connections/pat/:id`, session only, body = the `vault_access`/`default_access` pair; an empty body is 422, an edit always says what the credential gets). Both return the row as `GET /api/connections` serializes it. OAuth (`Connections.update_oauth_grant_access/4`): rewrites EVERY live row of the family, the consumed rotation parent included (a grace re-issue copies its parent, so leaving the parent would restore the old access), with the same columns consent writes (`OAuth.grant_columns/3`, fail-closed encoding included). Grant lock first, then the rows `FOR UPDATE` by id, rotation's order: a rotation either finished and is rewritten, or waits and copies the rewritten row. Issued access tokens read levels from the row via `gid`, the `:oauth_grant` entry is evicted here (`grants_changed/1`) and on every node by the `oauth_refresh_tokens_changed` trigger, and the user's sockets reconnect, so the change holds at once. Widening is allowed (the user is the grantor). An `mcp:read` grant is refused write with 422 rather than silently capped (`from_claims/1` would cap it anyway). API keys (`Accounts.update_api_key_access/3`): replaces `api_key_vaults` + `default_access` in place under `FOR UPDATE`, raw key unchanged, `:api_key` evicted locally and by the `api_keys_changed`/`api_key_vaults_changed` triggers. A pre-levels key (`default_access` NULL, plain hash) is refused with 422: an old release reads its rows as write, so giving it read levels would widen on a rollback; the user creates a new key. Pinned by `test/engram/connections_update_access_test.exs`.
- **Connections list `vault_ids`**: for a leveled credential, the vaults it reaches right now (as `vault_levels` shows), nil only when unrestricted; `new_vaults` carries the policy. The rollback sentinel is never listed.
- **Restore and the deleted list** use the vault's LISTED level (`Permissions.explicit_level/2`), never the new-vaults policy: restore needs an explicit write, and `GET /api/vaults?deleted=true` shows only explicitly held vaults. A vault deleted before the credential existed is recorded `none` at creation, so it is neither listed nor restorable, and stays unreachable after a session restores it. "Every live vault at write, policy write" collapses to the unrestricted NULL grant only when nothing is in the trash (new and stale SPAs store the same grant either way, pinned field by field and by behaviour in `vault_access_compat_test.exs`); with a trashed vault it stays leveled with that vault `none`, exactly like an API key. As defence in depth any OAuth grant with a `gid`, and any API key, cannot restore or list a vault deleted before the credential was created (a key by its `created_at`) (`OAuth.granted_at/1`: the `oauth_refresh_tokens.granted_at` column, set at exchange and copied on rotation, so cleanup never moves it; NULL rows from before the column fall back to the family's earliest `inserted_at` and heal on their next rotation; second precision). An unrestricted API key (no levels to record the trash in) is bound the same way by `created_at`.

### Vault resolution per tool call

MCP is stateless JSON-RPC, so the server keeps no active vault between calls. Every vault-scoped tool takes an optional `vault_id` (name or UUID). A bare call resolves to the credential's only reachable vault, or errors when it can reach several (`McpController.resolve_mcp_vault/3`). Never fall back silently to `is_default`: that flag exists for single-vault and onboarding convenience, and using it to disambiguate several vaults was #985.

## How to add a client manually (for debugging / local CLI scripts)

```bash
# Register via DCR — no admin involvement
curl -X POST https://mcp.engram.page/oauth/register \
  -H "Content-Type: application/json" \
  -d '{"redirect_uris":["http://localhost:9999/cb"],"client_name":"my-cli"}'

# Returns {"client_id":"<uuid>","client_id_issued_at":..., ...}
```

Use the returned `client_id` in a normal authorize → token flow. PKCE is mandatory.

## How to revoke a refresh token

```bash
curl -X POST https://mcp.engram.page/oauth/revoke \
  -H "Content-Type: application/json" \
  -d '{"token":"engram_oauth_rt_...","client_id":"<uuid>"}'
```

Returns 200 per RFC 7009 §2.2 once the client authenticates, except an access token (400 `unsupported_token_type`, §2.2.1) or a missing/non-string `token` (400 `invalid_request`). If `client_id` doesn't own the token, it's a silent no-op (token survives — leaking the distinction would help an attacker enumerate live tokens). Revoking a token in a refresh family also burns the rest of the family if any consumed-or-revoked replay is later detected. Revoking a refresh token revokes its whole family (RFC 7009 §2.1: the grant's access tokens die with it, answering 401 at once) and disconnects the owner's sockets.

## Database schema

| Table | Tenanted? | Purpose |
|-------|-----------|---------|
| `oauth_clients` | No (shared, pre-login) | DCR-registered clients, PK `client_id` (UUID) |
| `oauth_authorization_codes` | No (looked up by hashed code, pre-token) | One-time codes, 10-min TTL, sha256-hashed |
| `oauth_refresh_tokens` | No (looked up by hashed token) | 90-day rotation w/ `family_id` for reuse detection |

All three skip RLS — they're keyed by client_id or token-hash and looked up before user identity is established. Cleanup runs hourly via `Engram.Workers.CleanupDeviceAuthWorker`. It deletes a revoked family WHOLE once its revocation is past the 7-day grace (deleting only its revoked rows could leave an unrevoked one and, with "no revoked row" liveness, revive the grant), and expired rows one by one only in families with no revoked row.

## Spec conformance notes (#1977)

Audited against MCP 2025-11-25 authorization, OAuth 2.1, RFC 8414/9728/7591/7636/8707/9207/7009/6750/7523 and the CIMD draft. Deliberate deviations, each kept because tightening it breaks a named client:

- ChatGPT declares `private_key_jwt` but exchanges as a public client; accepted because its document lists `none` as permitted.
- Custom-scheme redirects (`cursor://`) are admitted; MCP wants https or localhost, Cursor desktop needs this.
- The loopback any-port rule also covers the `localhost` hostname (RFC 8252 prefers IP literals); Claude Code registers `localhost`.
- The root `/.well-known/oauth-protected-resource` on app/api/self-host hosts advertises `.../api/mcp` rather than the root; clients that fall back to it compare it to the URL they dialed.
- No DPoP/mTLS sender-constrained tokens: no MCP client sends them.
- `/api/mcp` accepts more than OAuth tokens: API keys (Free and paid users connect with them), Clerk sessions and device tokens. MCP says the server MUST NOT accept tokens not issued for it; one direction holds (an MCP token reaches nothing else), the other is kept for API-key users.
- A replayed code past its 10-min expiry revokes nothing: a callback page reloaded later is not an attack.
- `iss` (RFC 9207) is emitted on every authorization response (success, error, both Cancel paths) and advertised. It shipped staged in 0.53.0 so the SPA that forwards it was in prod first: a client SHOULD discard an unadvertised `iss` and MUST reject a missing one once advertised (§2.4).
- A token request that omits `redirect_uri` is accepted (OAuth 2.1 §4.1.3 / §10.2: 2.1 clients do not send it); present, it must match. RFC 6749 §4.1.3 required it when authorize named it; PKCE binds the code instead.
- A replayed code inside the 60 s grace window revokes nothing (§4.1.2 says SHOULD revoke): a client retrying its own in-flight exchange must not lose the grant it just got.
- Repeated `resource=` keys: Plug keeps the last one, so `resource=evil&resource=ours` validates on `ours` (RFC 8707 wants `invalid_target`). The `resource[]=` list form is checked in full.
- A CIMD document served `no-cache`/`no-store` is cached 5 min anyway (the TTL floor), so a hot client does not fetch per authorize.
- `/oauth/revoke` answers `unsupported_token_type` for any valid access JWT, not just the caller's: the JWT carries no client claim, and the holder of a token can test it by using it anyway.

Vendor flows: `test/support/oauth_flow.ex` + `test/engram_web/oauth_vendor_flow_test.exs` replay 14 real client shapes from prod `oauth_clients` rows end to end. Add a vendor there when one first connects; never guess a fixture.
